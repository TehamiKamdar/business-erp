TRADEFLOW ERP — API POST JSON REFERENCE

Note: - This document covers modules worked on so far. - UUID
placeholders such as PRODUCT_UUID must be replaced with real database
UUIDs. - Some Product Catalog, Supplier, Purchase Request and Purchase
Order payloads below are reference examples and must be checked against
the exact controller validation before use. - GRN, Stock Adjustment and
Stock Transfer payloads reflect the implemented workflows discussed so
far. - All endpoints assume the authenticated API base URL and required
Sanctum authentication headers.

1. PRODUCT CATALOG

1.1 Create Category POST /api/categories

{ “name”: “Electronics”, “code”: “ELEC”, “description”: “Electronic
products”, “status”: “active” }

1.2 Create Unit POST /api/units

{ “name”: “Piece”, “short_name”: “PCS”, “status”: “active” }

1.3 Create Brand POST /api/brands

{ “name”: “Samsung”, “status”: “active” }

1.4 Create Product POST /api/products

{ “category_id”: “CATEGORY_UUID”, “brand_id”: “BRAND_UUID”, “name”: “LED
Television”, “sku”: “TV-001”, “description”: “LED Television”, “status”:
“active” }

1.5 Create Product Unit POST /api/products/{product_id}/units

{ “unit_id”: “UNIT_UUID”, “is_base_unit”: true, “conversion_factor”: 1,
“is_purchase_unit”: true, “is_sale_unit”: true, “status”: “active” }

1.6 Create Product Price POST /api/products/{product_id}/prices

{ “unit_id”: “UNIT_UUID”, “price_type”: “sale”, “min_quantity”: 1,
“price”: 25000, “effective_from”: “2026-11-10” }

3. PURCHASE REQUESTS

3.1 Create Purchase Request POST /api/purchase-requests

{ “branch_id”: “BRANCH_UUID”, “warehouse_id”: “WAREHOUSE_UUID”,
“request_number”: “PR-001”, “required_date”: “2026-11-15”, “notes”:
“Stock replenishment”, “items”: [ { “product_id”: “PRODUCT_UUID”,
“unit_id”: “UNIT_UUID”, “quantity”: 50, “notes”: “Urgent requirement” }
] }

3.2 Purchase Request Workflow POST /api/purchase-requests/{id}/submit
POST /api/purchase-requests/{id}/approve POST
/api/purchase-requests/{id}/reject POST
/api/purchase-requests/{id}/cancel

These workflow requests were discussed as action endpoints. Check the
relevant controller validation if an action requires a request body.

4. PURCHASE ORDERS

4.1 Create Purchase Order POST /api/purchase-orders

{ “supplier_id”: “SUPPLIER_UUID”, “branch_id”: “BRANCH_UUID”,
“warehouse_id”: “WAREHOUSE_UUID”, “purchase_request_id”:
“PURCHASE_REQUEST_UUID”, “order_number”: “PO-001”, “order_date”:
“2026-11-10”, “expected_delivery_date”: “2026-11-15”, “notes”: “Regular
purchase”, “items”: [ { “product_id”: “PRODUCT_UUID”, “unit_id”:
“UNIT_UUID”, “quantity”: 40, “unit_cost”: 500, “notes”: “Standard
quality” } ] }

Note: purchase_request_id is optional when creating a direct Purchase
Order.

4.2 Purchase Order Workflow POST /api/purchase-orders/{id}/submit POST
/api/purchase-orders/{id}/approve POST /api/purchase-orders/{id}/cancel

The workflow action requests were discussed as empty-body POST requests.
Check controller validation if your current implementation requires
additional fields.

5. GOODS RECEIPTS (GRN)

5.1 Create Goods Receipt POST /api/goods-receipts

{ “purchase_order_id”: “PURCHASE_ORDER_UUID”, “receipt_number”:
“GRN-001”, “receipt_date”: “2026-11-10”, “supplier_delivery_number”:
“DEL-001”, “notes”: “Goods received”, “items”: [ {
“purchase_order_item_id”: “PO_ITEM_UUID”, “received_quantity”: 10,
“notes”: “Received in good condition” } ] }

5.2 Update Draft Goods Receipt PUT /api/goods-receipts/{id}

Use the same general structure as the create request, with the updated
header and items.

5.3 Post Goods Receipt POST /api/goods-receipts/{id}/post

Request body: empty.

5.4 Cancel Draft Goods Receipt POST /api/goods-receipts/{id}/cancel

Request body: empty.

6. STOCK ADJUSTMENTS

6.1 Create Stock Adjustment POST /api/stock-adjustments

{ “warehouse_id”: “WAREHOUSE_UUID”, “adjustment_number”: “ADJ-001”,
“reason”: “Physical stock count”, “notes”: “Monthly stock verification”,
“items”: [ { “product_id”: “PRODUCT_UUID”, “counted_quantity”: 95,
“notes”: “Physical count completed” } ] }

Note: system_quantity and difference_quantity are calculated by the
backend. Quantities are stored in the product’s base unit.

6.2 Stock Adjustment Workflow POST /api/stock-adjustments/{id}/approve
POST /api/stock-adjustments/{id}/post POST
/api/stock-adjustments/{id}/cancel

The workflow action requests were discussed as empty-body POST requests.
Check controller validation if your current implementation requires
additional fields.

7. STOCK TRANSFERS

7.1 Create Stock Transfer POST /api/stock-transfers

{ “source_warehouse_id”: “SOURCE_WAREHOUSE_UUID”,
“destination_warehouse_id”: “DESTINATION_WAREHOUSE_UUID”,
“transfer_number”: “TR-001”, “notes”: “Warehouse stock transfer”,
“items”: [ { “product_id”: “PRODUCT_UUID”, “unit_id”: “UNIT_UUID”,
“requested_quantity”: 10, “notes”: “Transfer 10 pieces” } ] }

7.2 Dispatch Stock Transfer POST /api/stock-transfers/{id}/dispatch

Request body: empty.

7.3 Receive Stock Transfer POST /api/stock-transfers/{id}/receive

{ “receipt_number”: “TR-REC-001”, “notes”: “Pieces received”, “items”: [
{ “stock_transfer_item_id”: “TRANSFER_ITEM_UUID”, “received_quantity”:
6, “notes”: “6 pieces received” } ] }

Partial receiving is supported. For example, if 10 units were
dispatched, receive 6 in the first receipt and 4 in a later receipt.

7.4 Cancel Draft Stock Transfer POST /api/stock-transfers/{id}/cancel

{ “reason”: “Transfer no longer required” }

IMPORTANT TESTING NOTES

1.  Replace every placeholder UUID with a real UUID from your database.
2.  Use Content-Type: application/json.
3.  Send the required Sanctum authentication credentials/token for
    protected routes.
4.  The exact Product Catalog, Supplier, Purchase Request and Purchase
    Order field names must be verified against the current controller
    validation. Their JSON here is a reference example, not a guarantee
    of exact validation.
5.  Do not assume every workflow endpoint accepts an empty body without
    checking its controller. In particular, cancellation endpoints may
    require a reason or notes field.
6.  Stock Adjustment quantities are handled in base units by the
    backend.
7.  Stock Transfer dispatch deducts stock from the source warehouse.
    Receiving adds stock to the destination warehouse and supports
    partial receipts.
8.  Stock Reservation workflow and Sales Order APIs are not included as
    implemented endpoints because their workflow is still pending.
